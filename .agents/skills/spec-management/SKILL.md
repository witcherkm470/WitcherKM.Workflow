---

Прочитай исходный запрос, docs/specs/README.md и затронутые canonical-файлы. Domain владеет понятиями/инвариантами, Application — сценариями/внешними проверками, UI — наблюдаемыми действиями; architecture — техническими решениями. На чужое правило ссылайся, не копируй его.

**Change spec → canonical specs → code.** Для отслеживаемого изменения создай один docs/specs/changes/active/<change>.md на цель: источник, меняемое поведение, затронутые canonical, критерии, вопросы и план проверок. При аудите перечисли неизменённые требования и найденные расхождения. Не создавай actual/changes в каждом слое.

Сначала внеси явно заданное изменение требования в canonical; затем реализуй. Canonical — согласованное действующее требование, а active честно показывает временное отставание кода. Не жди реализации, чтобы задним числом описать её как spec. Исправление бага не требует ослабления canonical.

Перед архивированием проверь каждый критерий, diff требований, сохранность исходников/ссылок и доказательства из [testing](../testing/SKILL.md). Перенеси завершённый change в archive с итогом; незавершённое оставь active с причиной. Архив не второй canonical. Не разрешай открытый вопрос без продуктового основания.
